3. Run all four bounded preflights concurrently
==============================================
After the source audit passes:

  sbatch --array=0-3%4 slurm/publication_preflight.sbatch

The command-line override raises independent job concurrency from the file's
default %1 to %4. It does not change four collectors per job, the learner or RNG.
Concurrent peak requested resources are 16 CPUs and 64GB across four allocations.
The scheduler may still serialize them. Each allocation remains 2h/4 CPUs/16GB.

Array mapping (seed 991, excluded from research results):
  0 PP Real, H=80; 1 PCP Real, H=80;
  2 FC Real, H=300; 3 PCP Binary-16, H=80.
Every job uses 100 updates, 4 collectors and a 500-step floor per collector.
Default fresh output: runs/hetnet_preflight_ARRAYJOBID/TASK_VARIANT/seed991/.
Leave PUBLICATION_PREFLIGHT_ROOT unset unless an explicitly fresh root is needed.

For C=4, b=500 and horizon H, each update collects between 4b and 4(b+H-1)
steps. Therefore these 100-update checks collect 200000..231600 steps for PP/PCP
and 200000..319600 for FC. They preserve production workload shape while keeping
validation bounded. Training speed/convergence is not established by this bound.

Required go/no-go evidence for EACH workload:
  - Successful scheduler exit; exactly 100 updates in preflight.json.
  - A validated model/optimizer checkpoint and frozen_checkpoint_probe with
    episodes=1 and parameters_unchanged=true (strict archived loading exercised).
  - Four collector records, one Torch thread each, SLURM allocation=4 CPUs;
    inspect affinity to ensure collectors can use the assigned CPU set.
  - No OOM/time-limit/worker exit; inspect Slurm memory accounting plus per-process
    resource records. MaxRSS per task/process is not simultaneous whole-job RSS.
  - Finite positive throughput and update/checkpoint times. Review
    projected_segment_hours_including_logging_and_checkpoints_excluding_startup
    as an estimate, not a full-budget runtime guarantee. If above 46h, plan a
    continuation; do not silently reduce the scientific sample target.

Scheduler check (replace PREFLIGHT_JOBID with the returned array ID):
  sacct -j PREFLIGHT_JOBID --format=JobID,State,ExitCode,Elapsed,AllocCPUS,ReqMem,MaxRSS

If an element hits the 2h allocation, the preflight is incomplete even if a
periodic checkpoint exists. Diagnose the resource/runtime log, then rerun that
bounded workload in a fresh directory with an appropriate allocation. Queue
delay plus audit/preflight time prevents a guaranteed start time tonight.

5. Monitor progress and continue correctly
==========================================
Look for increasing update/step counts in tagged stdout and updates.jsonl. The
first periodic checkpoint is after ten completed epochs (=100 updates). Preserve
source archives and logs. Check scheduler accounting and run_status.json; exit 0
or Slurm COMPLETED does not necessarily mean the sample budget is complete.

At the internal 46h timer the learner completes its current update, saves recovery
state, and returns normally with stop_reason=paused_wall_time and
scientific_budget_completed=false. Resume from run_status.json's EXACT checkpoint
path into a fresh segment using the already prepared batch file:

  sbatch slurm/publication_resume.sbatch \
    --run-dir ORIGINAL_RUN_DIRECTORY \
    --checkpoint EXACT_RECORDED_CHECKPOINT_PATH \
    --output FRESH_CONTINUATION_DIRECTORY

The 46h clock starts after setup. The 48h allocation supplies a provisional 2h
buffer for startup/remaining update/checkpointing, not an interruption guarantee.
SIGTERM exits immediately; periodic checkpoints are the abrupt-stop fallback.
Requeue/rerunning the training script does not restore Python state. Keep the
scientific budget until status and actual counts confirm budget_completed.
